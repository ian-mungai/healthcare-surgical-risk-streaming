# Surgical risk streaming

A self-hosted data platform that takes real surgical monitor recordings from ingestion to reporting.

In development. The first phase builds the host and its lifecycle. It adds the repository checks, the AWS grants and the Terraform and Ansible code for the host. It also adds the deploy workflow and the commands that create, stop, start and destroy the host.

## Install

You need macOS on Apple silicon or Linux on x86-64, the two platforms that `scripts/quality/install_tools.py` pins tools for, with Python 3.14, Git, GNU Make and curl. The host commands also need the AWS CLI, OpenSSH and the Tailscale client. Reading AIStor's licence from this computer's OpenBao also needs the macOS Keychain (the `security` command): without it the deploy skips AIStor with a notice and goes on (see the AIStor licence step below).

```sh
make setup  # create .venv, install the pinned tools (gitleaks, Terraform 1.16.4, tflint, Trivy), the commit and commit message hooks, the working-tree privacy hook and the pre-push hook
```

`infra/versions.tf` requires Terraform 1.16.4 or a later 1.16 release, and the hosted CI job installs 1.16.4.

The host commands read their settings from `.env`. Copy `.env.example` to `.env` and set `AWS_REGION`, `AWS_PROFILE`, `AWS_ACCOUNT_ID`, `PROJECT_NAME`, `ENVIRONMENT` and `S3_BUCKET`. Git ignores `.env`. The example file also names the optional Tailscale, evidence and service group settings.

## Usage

Each check runs at the cheapest layer that can do its job, and hosted CI runs every check in full.

1. **Commit hooks, about 90 seconds:** secrets in the staged changes, credential and data files, privacy, Ruff, MyPy, the quick tests (`tests/fast`) and the commit message.
2. **Push gate, about 40 seconds for one commit (2 minutes at most), before every push to any branch** (a plain Git `pre-push` hook that `make setup` installs, `scripts/quality/push_gate.py`): it reads what Git sends and checks every commit that the remote ref in Git's input does not hold, and the whole history for a new ref, because the receiver's history is not known. It refuses a push while tracked files have uncommitted changes, then runs the secret scan of the diffs (merge diffs included) and of whole commit messages, the commit messages, the privacy scan, the changed files' own checks (Ruff, MyPy, Terraform's formatter and the quick test modules that cover the changed files; a rename or delete of a Python file runs the whole quick group) and the dependency scan when a lock file changes. One hook is shared by every worktree and refuses a push from a worktree whose gate is missing or older than the version that `make setup` installed it for (run `make setup` or rebase). A push that sends nothing, or only deletes, runs nothing. There is no full local run before a push.
3. **Hosted CI** (`.github/workflows/ci.yml`): every check in full on each push of a work branch, each pull request, the commit that a squash merge creates on `main`, every Monday and on demand. The manual-stage hooks also scan every lock file (Trivy) and every commit message of the history for secrets. A separate headroom job, outside the required check, waits for the required job and fails any job that used over 80% of its timeout, is missing from the run or has no limit. `main` moves only through a pull request that is up to date with `main` and squash-merged after the required check passes (a recorded exception to the check-first default).

Recorded limits of the push gate (owner, Nov 23 2026, "A"; neither skips a check that publishes data):

- With `diff.renames=false` in a Git configuration, Git reports a rename as a delete and an add, so the changed-file checks select fewer quick test modules. The hosted run still runs every test.
- A `make setup` run from a worktree that holds an older gate can leave a pre-push hook that calls itself. It blocks the push and never skips a check.

The privacy scan in the gate reads the tracked blobs of the pushed commit, not the working tree, so a sparse checkout cannot hide a file from it.

Terraform providers are pinned by hash in `infra/.terraform.lock.hcl` and are not vulnerability-scanned: Trivy 0.76.2 detects no package in a Terraform lock file.

Run the checks from the repository root.

```sh
make check            # run the manual-stage hooks on every file
make test-fast        # run the fast tests
make test-slow        # run the slow tests: Ansible playbook runs, local servers and stand-ins, and the planted workflow faults (on demand; the hosted run runs them too)
make headroom         # in a hosted run only: check every job of the run against its timeout (GH_TOKEN, GITHUB_REPOSITORY and GITHUB_RUN_ID are set there)
make test-guards      # commit planted faults in a temporary repository and confirm each guard refuses its own
make test-guards PARALLEL=8  # the same, as 8 shards at once in one process within the free cores and memory, with one run record (SHARD=1/8 runs one share)
make test-deadline    # run a wait that passes its deadline and confirm it fails visibly
make check-terraform  # check the Terraform code with its plan tests, tflint and Trivy
make check-ansible    # check the Ansible playbook syntax
```

Each end-to-end run writes `record.json`, `log.txt` and `retention.json` in a new folder under `runs/`, which Git ignores. Hosted CI keeps the record and retention label of each guard shard and of the deadline case as an artifact for 30 days.

`make images-push` builds each project image from the tracked files of HEAD, pushes it when `compose/image_pins.yml` lacks its tag and pins the digest that the push reports. The pin file is the authority and the command never reads the registry. A push that succeeded but whose pin was not saved is pushed again on the next run and may overwrite that unpinned tag. Nothing pins it, so no host pulls it. The host pulls only the pinned digests. Before the first push, the command scans every image that it built with Docker Scout, which uses the same Docker sign-in. A fixable finding in any of them pushes nothing, unless the active list of `image_scan/accepted_findings.yml` has an entry for that image and each artifact that holds the package, with the ID, the package version, the reason that no release fixes it and the date. The gate never reads the file's pending list, whose entries wait for the owner's decision. The active list is empty, so the gate refuses the current Spark image. A failed scan or an incomplete report pushes nothing either. A report counts as complete only when the scan ends with the exit status 0, no object in the report holds a key twice and, when the report holds invocations, every one says that its execution succeeded. The reports of Docker Scout 1.28.0 hold no invocations, so for them the exit status decides. An image that is already pinned is not scanned again.

Each host command runs under the project's AWS profile named in `.env`.

```sh
make host-up                      # save a plan for review, or with CONFIRM=<code> apply it and set up the host
make host-stop                    # stop the host and keep its disk
make host-start                   # start the host again
make host-runners-place RUNNERS="tests/e2e/silver_signals.py ..."  # place named Git-ignored runner files in the runner folder of the deployed commit
make inventory                    # list every resource the run created
make evidence-export              # pack the run's evidence with a manifest
make evidence-verify              # check the export and sign its receipt on the owner's computer
make teardown-plan                # save the destroy plan and record what may be deleted
make host-destroy CONFIRM=<code>  # destroy only after every guard passes
make storage-up                   # save a plan for the AIStor bucket for review, or with CONFIRM=<code> apply it and check the bucket's versioning
```

AIStor keeps its root user and password only in root-only files on the host (mode 0400, made once at the first deploy, given to the server through `MINIO_ROOT_USER_FILE` and `MINIO_ROOT_PASSWORD_FILE`). Nothing uses them for the project's work, and the deploy uses them on the FIRST bootstrap of a host only. That bootstrap reads the pair inside the AIStor container to make two accounts: the project user (only when the server says it does not exist) with its policy, exactly the S3 calls that the pinned Terraform provider makes for the bucket and its versioning, on the one bucket, with no object action, no bucket-policy write and no version delete; and a read-only audit identity (`project_audit`) whose one policy allows only the admin reads `admin:GetUser` (a user's policies, status and groups) and `admin:GetPolicy` (a policy's document) and no S3 call. Each account holds its policy and no other policy and no group; a policy or group that someone added is removed before a disabled user is enabled. The two passwords are root-only files on the host. OpenBao is given each pair only after that pair has signed in (`secret/services/aistor/aistor` for the project user, which only the `aistor` role reads, and `secret/services/aistor/audit` for the audit identity, which only the deploy's admin role reads), so a password file that was lost and made again never replaces a working value. The bootstrap ends by writing a root-only marker file on the host (`/opt/platform/compose/aistor.bootstrap`, mode 0400, beside `aistor.state`), and a run that fails before that is the first bootstrap again.

Every later deploy makes no call with the root pair and no write. It reads the live state as the audit identity and the project user with the pairs that OpenBao keeps, and checks that the project user is enabled, holds exactly the project policy by name and no other policy, is in no group (it reads the user's raw admin answer, `GET /minio/admin/v3/user-info`, with the AIStor container's curl, because `mc admin user info` also reads each group's description, which needs `admin:GetGroup`, and the audit identity holds only `admin:GetUser` and `admin:GetPolicy`; an added group is named in the message), and that the project policy's document equals the desired one; then it lists the project's bucket as the project user. A difference, a refused sign-in or a missing OpenBao entry fails the deploy with a fixed message that names what differs and changes nothing. An `AccessDenied` answer (an offline or unlicensed server gives it too) is a failure and never a reason to use root. The root pair is used again only when the owner approves it for one run, by running the launcher directly with its own flag, `.venv/bin/python -m scripts.infra.host up --confirm <code> --aistor-repair` (`make` never passes it, so no make variable, environment value or `MAKEFLAGS` can approve a repair). The flag passes the extra variable `aistor_repair_once` as true to the AIStor playbook of that one run and to no other playbook; every other run passes it as false, and an extra variable outranks any inventory value of the same name, so no file can turn the repair on. No file holds the approval, so the next `make host-up` is a plain run again and a repair that was done never repeats. The approval is not an inventory variable, and the old inventory variable `compose_stack_aistor_root_repair` is refused whatever its value: the AIStor step stops with a message that names it and asks for it to be removed. That repair removes what is not the project's, restores what is missing and, for an account that exists and that neither OpenBao's sign-in nor the password file signs in as, sets the password file's value on it. A host that was bootstrapped before the marker existed gets it with one root run that changes nothing else. If the host's AIStor data is replaced while the marker stays, the next deploy fails closed (no project user) and needs the same approval (the launcher's `--aistor-repair` on that one run). `make storage-up` and every other storage client sign in as the project user, which is also Terraform's identity (bucket-only, never the audit identity); workloads use STS. `make storage-up` first refuses a provider lock (`infra/storage/.terraform.lock.hcl`) that holds no registry hashes and names the owner's step (`.tools/bin/terraform -chdir=infra/storage providers lock -platform=<this computer's platform> -platform=linux_amd64`, then commit the file), and it refuses a sign-in in OpenBao for any account but the project user before Terraform starts.

AIStor's licence (the Free licence from MinIO) is kept in this computer's OpenBao at `secret/aistor_licence`, field `value`. `make host-up` reads it with a token of its own from the Keychain item `openbao-aistor-licence-token`, never with the owner's full token (`openbao-owner-token`), and places it on the host as one root-only file (mode 0400, the file that the server reads through `--license`, as the AIStor container install guide shows) through a script that sudo does not record; it is never printed, logged or put in an Ansible variable. The token's OpenBao policy `aistor-licence-read` allows `read` on `secret/data/aistor_licence` and nothing else.

The owner makes that token once, in a separate terminal so no value reaches a chat (`references/local_machine.md`, Local secrets). The policy and the token need administration rights that the owner's token (`owner-secrets`) does not have, so first generate a root token with the unseal key as item 3 of that section says (`bao operator generate-root`) and revoke it at the end of these steps. The token is made with `-orphan` because a token that is made as a child of the administration token is revoked with it by `bao token revoke -self` ([token hierarchies and orphan tokens](https://openbao.org/docs/concepts/tokens/#token-hierarchies-and-orphan-tokens)); `-orphan` needs the root token's rights. Then run, in this order (the token is never printed: it goes to the clipboard, then into the Keychain at `security`'s own hidden prompt, and then the clipboard is cleared):

```zsh
export BAO_ADDR=http://127.0.0.1:8200
read -rs "BAO_TOKEN?Administration token: " && export BAO_TOKEN; echo
bao policy write aistor-licence-read - <<'POLICY'
path "secret/data/aistor_licence" { capabilities = ["read"] }
POLICY
bao token create -field=token -orphan -policy=aistor-licence-read -no-default-policy -period=768h | pbcopy
bao token revoke -self; unset BAO_TOKEN
security add-generic-password -a "$USER" -s openbao-aistor-licence-token -U -w   # paste at the hidden prompt, twice
pbcopy < /dev/null
```

Save the licence itself with the command in `references/local_machine.md` (item 5), with the name `aistor_licence`. Then check, after the administration token is revoked, that the saved token still works. The command reads the licence path with the token from the Keychain item, in the environment of that one command, and sends the value to `/dev/null`, so nothing is printed. An empty token stops the command before `bao` runs, because `bao` would use its token helper file instead. A 403 answer means the token or its policy is wrong (make the token again from `bao policy write`), and a 404 answer means that the licence is not saved yet:

```zsh
export BAO_ADDR=http://127.0.0.1:8200
token="$(security find-generic-password -a "$USER" -s openbao-aistor-licence-token -w)" && [[ -n "$token" ]] && BAO_TOKEN="$token" bao read secret/data/aistor_licence > /dev/null && echo "The licence token reads the licence path."; unset token
```

A periodic token expires after 768 hours without a renewal, and the unseal job renews only `openbao-agent-token` and `openbao-owner-token`: when the launcher says that OpenBao refused the read (HTTP 403), run the steps again from `bao policy write` with a new administration token.

A computer without that Keychain item, or without the `security` command (Linux), has no licence source. A licence that OpenBao does not hold is the same case for the deploy: nothing is sent, and the deploy goes on with everything else (Airbyte, the connection step and the rest). The stack's pull leaves AIStor's image out; only the AIStor step's start pulls it, when the licence is on the host, so a deploy without a licence needs nothing from its registry. `make host-up` tells the AIStor playbook only one non-secret fact, `placed` (the licence is on the host) or `absent`. With `placed`, a licence file that is missing on the host fails the AIStor step. With `absent` and no licence file on the host, the playbook skips AIStor and writes `skipped` to `/opt/platform/compose/aistor.state`, and only then does `make host-up` read that record and print the notice (it names this step when the cause is a missing token); with `absent` and a licence file already on the host, AIStor starts with that file and the notice says so. Save the licence, make the token if it is missing and run `make host-up` again: AIStor starts and the record says `started`. `make storage-up` reads that record first and, for a skipped AIStor, names this step.

An interrupted placement can leave a second `0400` file, `.licence.<8 hex>.new`, that holds a copy of the licence. The placement script removes it when the SSH session drops or the script is told to stop (a hangup or a termination), and every deploy's licence check removes any that is left by a kill that cannot be caught, before the licence is read.

The deploy also makes one runner folder on the host for the native host-mode runners: `/opt/platform/runner/<commit>`, owned by the SSH user, mode 0750 and holding no secret. The runner folder and the commit's folder must be real folders (a link is never followed, written through or kept as a finished folder). It holds the deployed commit's tracked files from `git archive` (no Git history, no ignored or uncommitted file) and a `.venv` built from the hash-pinned `requirements.txt` with `--require-hashes` and `--only-binary :all:`. The role that makes the folder is the last role of the host playbook. It makes and reads the archive on the controller first, before it installs the interpreter or changes anything else on the host: a commit that the repository does not hold, or a link, a device or an odd path in it, fails the deploy before this role changes the host (the changes of the earlier roles stay), and the files and hashes of that archive are the only expected files. The interpreter is Python 3.14.10 (the project's pin; Ubuntu 24.04 ships 3.12) from a python-build-standalone archive whose SHA-256 is pinned in `ansible/group_vars/all.yml`, kept in a folder of its own beside the others in `/opt/platform/python` (the version, `-runner_checkout-` and eight random characters) with a marker that names the archive's digest, written before the unpack, and published as the link `/opt/platform/python/3.14.10`: it is reused only for that digest, and a new one is unpacked into a new folder, run there and published only after it says its version, by one atomic replacement of the link (so an interrupted or failed install leaves the interpreter that was there). After the link changed, the other folders of that version that have both that name and a marker are removed; any other folder, such as an operator's copy, stays. A folder at `/opt/platform/python/3.14.10` that is not that link is refused and never removed. The deploy writes `runner_manifest.json` in the folder's root before the finished marker (`{"commit": "<40 hex>", "files": {"<path>": "<sha256>"}}` for every file that `git archive` placed, written only if the unpacked folder holds exactly the controller's files; not `.venv`, the marker or a placed runner; read-only to its owner). A second deploy of the same commit checks the marker, the manifest (it must equal the controller's archive: an empty, partial or extended map fails), every file and the environment (the interpreter runs and says the pinned version, and the installed packages equal the pins of the lock file whose environment marker is true for that interpreter): when nothing differs it changes nothing and keeps the placed runners, and otherwise it builds the folder again. A deploy of another commit, or of another interpreter pin, removes every other folder under `/opt/platform/runner` and builds the new one. Every command of the role runs under `timeout --kill-after`, so a command that never ends is stopped with its processes where it runs, and before anything in the runner folder or any older interpreter folder is removed, and after a failed build before any cleanup, no process that a build started (each unpack, environment and install command writes its process group in `/opt/platform/runner.build_processes`) or that works in the runner folder (its working folder or executable is under it, or its command line names it) may still work. A deploy that cannot look at the processes fails. A stopped host keeps the folder on its disk, and `make host-destroy` removes it with the disk. The folder changes nothing that the stack runs. The Git-ignored runners are not in the archive: `make host-runners-place` sends each named file (a `.py` file directly under `tests/e2e/`, or a `.py` or `.yml` file directly under `tests/e2e/stream_stack/`, where the streaming run's probes and its Compose overlay are; no other folder and nothing deeper; a file that Git ignores and the commit does not hold, a plain text file with one name and at most 1 MiB that passes the privacy scan and the pinned credential scanner gitleaks over the bytes that are sent; the imports of a `.py` file must resolve against the commit, and each package that a file directly under `tests/e2e/` reaches must be pinned in the commit's lock file) over SSH into a file that `mktemp` makes in the folder and moves into place, and records its SHA-256 in `placed_runners.json` in the folder's root (read-only to its owner; the runners placed earlier are hashed on the host first, and the record holds only hashes that the host computed; the manifest is never touched) and, as the host's record, in `runs/<run id>/runner_files.json`, so that a runner can check its own file. A path in either record is relative to the folder, in one of two forms: `tests/e2e/<name>.py`, or `tests/e2e/stream_stack/<file>`, a `.py` or `.yml` file; its whole form is `RUNNER_FORM` in `scripts/infra/runner_place.py` (`tests/e2e/(?:[a-z][a-z0-9_]*\.py|stream_stack/(?:[a-z][a-z0-9_]*\.py|[a-z][a-z0-9_]*(?:\.[a-z0-9_]+)*\.yml))`), and a reader of `placed_runners.json` on the host accepts exactly that form. Every folder on the way to a file that is missing, `tests/e2e/stream_stack/` included, is made for the SSH user only (mode 0700), and one that is a link or is no folder stops the placement. A probe runs in the replay or the Spark image with its folder on the import path: the packages that it reaches through the repository's modules come from the image and are not asked of the host's lock file, a package that a probe names itself must still be pinned there, a probe that imports another probe by its name needs that one in the same call, a wildcard import of another probe is accepted only when that probe has one plain top-level `__all__` list or tuple of string literals, names `__all__` nowhere else and binds each entry by an unconditional top-level `def`, `class`, plain assignment or import (a refusal gives the entry's position, never its text), and a `.yml` file is not read as Python. The names in `RUNNERS` reach the program as data, as the raw text that Make does not expand (a `$(VAR)` in a name stays as typed), and are split on white space in Python, never by a shell. The pinned scanner runs with its own configuration, an empty environment and no `gitleaks:allow` skip, so nothing in the shell, the working folder or the file changes what it finds, and the host's marker must be the role's JSON for exactly this commit before a file is received. On the host, run a runner from the folder: `cd /opt/platform/runner/<commit> && .venv/bin/python -m tests.e2e.<runner>`.

Each service belongs to the group that `compose/limits.yml` gives it. The always-on group (`supporting`) starts with the stack. Every other group is a Compose profile of the same name and starts when a job or an operator asks for it, after the admission check. Airbyte's workloads in k3s are scaled through the Kubernetes API. A group that does not fit the available memory waits and then fails with the check's four figures.

```sh
make group-up GROUP=<name>     # admit and start the group, and wait until its services are healthy
make group-down GROUP=<name>   # stop the group's services and leave every other service running
```

The shared PostgreSQL server has 100 connection slots and keeps 3 for superusers. `compose/postgres_connections.yml` gives each client (Temporal, Airbyte's pods, Apicurio, Nessie, Alloy and the three Dagster services) a maximum, and a fast test fails when the maxima and the margin pass 97, when a client is missing, or when a tracked file does not carry the cap that its entry states under the name that the fixed table of the test expects. `tests/slow/test_airbyte_rendered_environment.py` renders chart 2.5.0 and checks the same caps in the manifests (it needs `AIRBYTE_CHART_ARCHIVE` and Helm). When the start of the stack or the recreate of its stale services fails to become healthy, the failure message says "PostgreSQL connection slots are full" and shows how many sessions each account holds (a superuser's too), if that is the cause. Every Airbyte pool has a cap in `ansible/roles/airbyte/files/values.yaml`, and the Airbyte deployments that hold connections get the Recreate strategy in the manifests of every upgrade (a Helm post-renderer of the role) and are scaled to zero before a rollback, so an old and a new pod never hold slots together. The Dagster daemon runs backfills in its own thread (`backfills.use_threads: false` in `orchestration/dagster.yaml`, which the budget's fixed table checks), because Dagster 1.13.31 starts a pool of worker threads when the key is unset.

`group-up` starts AIStor only while `aistor.state` in the compose folder says `started`, the record that the deploy's AIStor step writes. With a `skipped` record, or none, it leaves AIStor out, says so and starts the rest of the group. The admission check still counts AIStor's memory.

The commands read the compose folder from `STACK_COMPOSE_DIRECTORY` (default: this repository's `compose`).

The patient assignment rule, one split by patient for all models, is in `scripts/sample/split.py`. Rebuild the candidate cases for the fixed sample with `.venv/bin/python -m scripts.sample.candidates check`.

## Lake layer identities

Each Spark job runs under the AWS role of one lake layer, so a job reaches only the warehouse folder of its own layer. Nessie's catalog keeps a table in the warehouse folder of its namespace, so a layer's prefix is `warehouse/<namespace>/`. `scripts/stack/job_workloads.py` names the workload of each job in `spark/jobs`, and `infra/environments/dev.tfvars` holds the grants.

| Workload | Reads | Writes and deletes | Compose service and profile |
| --- | --- | --- | --- |
| `bronze` | `landing`, `manifests`, `warehouse/raw_records`, `warehouse/bronze` | `warehouse/bronze` | `spark_bronze`, `batch_bronze` |
| `silver` | `warehouse/raw_records`, `warehouse/bronze`, `warehouse/silver` | `warehouse/silver` | `spark_silver`, `batch_silver` |
| `gold` | `warehouse/bronze`, `warehouse/silver`, `warehouse/gold` | `warehouse/gold` | `spark_gold`, `batch_gold` |
| `stream` | `warehouse/feature`, `warehouse/stream` | the same two prefixes | none yet |
| `maintenance` | `warehouse` (every table, for the tag checks) | writes the five layer folders and `warehouse/catalog_proof`, deletes nothing | `spark_maintenance`, `batch_maintenance` |

The Airbyte load owns `warehouse/raw_records`, and no workload role writes it. The table checks job runs as `bronze`, the reconciliation job as `silver` and the catalog proof as `maintenance`. Terraform refuses a grant that lets a workload write another layer's prefix (maintenance may write each layer's folder but never delete), write the whole warehouse prefix or `raw_records`, or delete in the whole warehouse prefix. The table maintenance job compacts only those folders and leaves `raw_records` out of its default table selection.

Every Spark service has the same entry point, `python -m spark.launcher <job> [arguments]`, and names its workload in `SPARK_WORKLOAD`. The launcher refuses a job that `job_workloads.py` does not map to that workload before Spark starts (`wrong_workload`, `unknown_job`, `no_workload`, exit 2), and with no job it prints its usage and exits 2. `make group-up` refuses a Spark group (`batch_<workload>`) before Compose starts a container (the command `python -m scripts.stack.groups up batch_<workload>` exits 1, and `make group-up GROUP=batch_<workload>` exits 2, because `make` reports a failed recipe with its own status 2 and prints the recipe's status as `Error 1`): the service starts no job by itself, and a stopped container of an older version would restart its old entry point. No supported command in the repository started a one-off before, so the manual one-off is now `scripts/stack/spark_run.py`, which holds the slot while its container exists. Run it in the code location container, where the table checks one-off runs too: `docker compose exec dagster_code_location python -m scripts.stack.spark_run table_maintenance --dry-run` (options `--wait-seconds` and `--deadline-seconds` come before the job). One Spark job runs at a time across the four services, because the memory figure assumes one: a Spark group waits in the admission check while any Spark service is alive (running, paused or restarting), and every supported Spark launcher (the table checks one-off, `spark_run`, and the end-to-end runners) starts its container with the one name `surgical-risk-spark-slot` (`--name` of `docker compose run`, [Docker](https://docs.docker.com/reference/cli/docker/compose/run/)) and an owner label. Docker creates a container name once at a time on an engine, so a second launch fails on the name and is reported as the slot being busy (`spark_run` exits 1). The slot is held as long as that container exists, so a killed client, a restart of the code location or a paused container does not free it. No launcher uses `--rm`: after success, failure, a deadline or an interrupt, every launcher stops and removes its own container (by ID, and only the one that carries its own owner label), reads the engine again and reports a container that survives with its ID and state. A job that passes its deadline exits 124 only when its container is gone, else `spark_run` refuses (exit 1); a finished job keeps its own exit status when the removal fails. The container that stays until this removal is also how a launcher knows that the engine created it: a start is tried again, within the wait that is left, only when Compose exits 1 with no output, with the whole name refusal of Docker Engine ([29.9.3](https://github.com/moby/moby/blob/docker-v29.9.3/daemon/errors.go#L55-L63)), and the engine holds no container of that launch, so a created job never runs twice. A container that is left over (its launcher was killed or restarted, or the removal failed) keeps the name, also after its job ends, and the slot stays busy: remove it with `docker container rm`. `--wait-seconds` and `--deadline-seconds` must be finite numbers of seconds (a wait of 0 or more, a deadline above 0), else `spark_run` exits 2; every read of the engine before a start during a wait gets the time that is left, no such read starts at or after the end of the wait, and a free reading at or after that end admits nothing. The Dagster runs of the Spark groups, the table checks job among them, share the run tag `surgical_risk/spark`, limited to one. A launcher builds that command with `job_command` in `scripts/stack/job_workloads.py` and never overrides the entry point.
